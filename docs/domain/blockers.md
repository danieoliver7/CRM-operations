# Operational Blockers

## Blocker Philosophy

Blockers exist to expose operational friction.

A blocker is NOT:
- a bug system
- ticket management
- incident platform

Blockers are lightweight operational impediments.

---

# Examples

- waiting for approval
- missing copy
- missing assets
- QA blocked
- missing audience validation
- missing links
- delayed scheduling

---

# Operational Goals

Blockers should:
- expose delays
- clarify responsibility
- improve coordination
- improve operational awareness

---

# UX Philosophy

Blockers should be:
- contextual
- visible
- lightweight

Avoid:
- enterprise incident management
- escalation systems
- excessive severity systems

---

# Blocker Severity Philosophy

Severity should remain simple:
- low: useful context, no immediate execution stop
- medium: operational gap that can delay the campaign
- high: blocker that can stop or seriously compress execution

# Blocker Visibility Rules

Blockers should appear:
- inside the campaign workspace
- near workflow and next-action context
- in dashboard execution warnings only when relevant

Blockers should not become:
- tickets
- incidents
- assignments
- threaded discussions
